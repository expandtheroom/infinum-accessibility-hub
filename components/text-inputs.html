Text Inputs

Accessible text input patterns covering labels, hints, error messages, and assistive technology support.

Design guidelines

UX guidelines

  • The label must always be visible above the input — never replace it with placeholder text alone, never use floating labels that disappear into the border on focus. A persistent, clearly readable label is required by WCAG 1.3.1 (Info and Relationships) and helps users with short-term memory difficulties who cannot re-read a disappeared placeholder while typing.
  • Placeholder text is supplementary only — use it to show an example value (e.g. "e.g. name@example.com") but never as the field's only label. Browser default placeholder contrast fails WCAG 1.4.3; always check and override it to meet at least 4.5:1.
  • Hint text must appear below the label and above any error message — provide format guidance (e.g. "DD/MM/YYYY"), character limits, or other constraints as persistent visible text, not only as placeholder or tooltip text. Position it consistently across the form.
  • Required fields must be indicated with an asterisk (*) accompanied by a visible legend at the top of the form explaining "* Required". Do not use "Optional" labels on every optional field (this becomes noisy); mark required fields and leave optional ones unmarked unless the form is mostly optional.
  • Input width should be proportional to the expected content length — a postcode field should be short; a "Full name" field should be wider. This acts as a visual affordance for how much text is expected, reducing cognitive load.

Visual design guidelines

  • Error messages must appear below the input in a consistent location — use a combination of a red/error color, an error icon, and a descriptive text message. Never rely on color alone (WCAG 1.4.1). The error message must remain visible until the error is resolved.
  • Design a clearly visible focus ring — specify the focus style in design files (color, width, offset). Do not leave it to browser defaults, which may be invisible in certain design contexts. Annotate that outline: 0 must never be used without a replacement.

Dev guidelines for web

  • Associate every input with a <label> via matching for/id attributes. Clicking the label moves focus to the input — an important usability benefit, especially for motor-impaired users on touch devices. Never use aria-label as a substitute when a visible label can be provided.
  • Link hint text via aria-describedby: <input type="text" id="phone" aria-describedby="phone-hint" /> with <p id="phone-hint">Include your country code, e.g. +44 7700 900000</p>. Screen readers announce the hint after the label when the user focuses the field.
  • On validation failure, set aria-invalid="true" on the input and add the error message element's id to aria-describedby (space-separated alongside any existing hint id). Remove aria-invalid or set it to "false" once corrected. Screen readers announce "invalid entry" alongside the label and role.
  • Use the appropriate type attribute — type="email", type="tel", type="url", type="number" — to trigger the correct on-screen keyboard on mobile and to enable browser-level validation. Use type="text" only when no more specific type applies.
  • Provide autocomplete attributes for personal data fields — e.g. autocomplete="name", autocomplete="email", autocomplete="tel", autocomplete="street-address". This enables browsers and password managers to prefill known values, which is essential for users with motor disabilities or cognitive impairments.
  • Never use outline: 0 or outline: none without providing a custom, clearly visible focus replacement. WCAG 2.2 SC 2.4.11 (Focus Appearance) requires a minimum area and contrast ratio for focus indicators. Specify your custom focus style explicitly in CSS.
  • Input borders must meet 3:1 contrast against the adjacent background — a common failure is very light grey borders on a white page. Input text must meet 4.5:1. Mark both requirements in your design system tokens to make them easy to audit.

<div>
  <label for="email-input">

    <span aria-hidden="true">*</span>
    <span class="visually-hidden">(required)</span>

    id="email-input"
    name="email"
    required
    autocomplete="email"

Dev guidelines for iOS

  • Always provide an .accessibilityLabel when the visible label is not read automatically — for custom-styled text inputs where VoiceOver may not pick up the associated label, set .accessibilityLabel("Email address") directly on the TextField to give it an explicit name.
  • Use .accessibilityHint to describe expected input format — add a hint such as .accessibilityHint("Enter your country code followed by your number, for example plus 44 7700 900000"). VoiceOver announces this after the label and value, giving users context without cluttering the visible UI.
  • Announce validation errors as live region updates — when an inline error message appears after failed validation, post a VoiceOver announcement using UIAccessibility.post(notification: .announcement, argument: "Invalid email address. Please enter a valid email.") so users who have already moved focus away still hear the error.
  • Use .accessibilityValue to surface the current field state — for fields that display a computed or derived value (e.g. a formatted phone number), use .accessibilityValue("plus 44 7700 900000") to communicate the current content in a screen-reader-friendly form alongside the label.
  • Mark decorative icons and prefix/suffix elements as .accessibilityHidden(true) — currency symbols, lock icons, and other visual decorations inside the input should be hidden from VoiceOver to prevent redundant announcements; their meaning should be conveyed through the label or hint instead.

Example code

import SwiftUI

struct AccessibleEmailField: View {
    @State private var email = ""
    @State private var hasError = false

    var body: some View {
        VStack(alignment: .leading, spacing: 4) {
            Text("Email address")
                .font(.subheadline.weight(.semibold))

            TextField("you@example.com", text: $email)
                .textContentType(.emailAddress)
                .keyboardType(.emailAddress)
                .autocapitalization(.none)
                .accessibilityLabel("Email address")
                .accessibilityHint("We'll use this to send your receipt")
                .accessibilityValue(email.isEmpty ? "Empty" : email)
                .overlay(
                    RoundedRectangle(cornerRadius: 6)
                        .stroke(hasError ? Color.red : Color.gray, lineWidth: hasError ? 2 : 1)
                )

            if hasError {
                Label("Please enter a valid email address.", systemImage: "exclamationmark.circle")
                    .foregroundColor(.red)
                    .font(.caption)
                    .accessibilityLabel("Error: Please enter a valid email address.")
            }
        }
        .onChange(of: email) { _ in
            if hasError {
                UIAccessibility.post(
                    notification: .announcement,
                    argument: "Error cleared. Enter a valid email address."
                )
            }
        }
    }
}

Dev guidelines for Android

  • Use Modifier.semantics { contentDescription = "..." } only when the visible label cannot be read automatically — for standard OutlinedTextField with a label parameter, TalkBack reads the label directly; override with contentDescription only if the label is purely visual or missing.
  • Set keyboardOptions to the appropriate keyboard type — use KeyboardType.Email, KeyboardType.Phone, or KeyboardType.Number to invoke the correct soft keyboard. Pair with autofill hints (AutofillType.EmailAddress, AutofillType.PhoneNumber) to support autofill for users with motor disabilities.
  • Communicate validation errors through isError and a supporting error message — set isError = true on the OutlinedTextField and provide a supportingText composable that TalkBack reads after the field label. Add Modifier.semantics { error("Please enter a valid email address.") } to programmatically expose the error state.
  • Use LiveRegionMode.Polite for error messages that appear dynamically — wrap the error text composable with Modifier.semantics { liveRegion = LiveRegionMode.Polite } so TalkBack announces changes to the error state without interrupting the user mid-interaction.

Example code

import androidx.compose.material3.OutlinedTextField
import androidx.compose.material3.Text
import androidx.compose.runtime.*
import androidx.compose.ui.Modifier
import androidx.compose.ui.autofill.AutofillType
import androidx.compose.ui.semantics.*
import androidx.compose.ui.text.input.KeyboardType
import androidx.compose.foundation.text.KeyboardOptions

@Composable
fun AccessibleEmailField() {
    var email by remember { mutableStateOf("") }
    var hasError by remember { mutableStateOf(false) }
    val errorMessage = "Please enter a valid email address."

    OutlinedTextField(
        value = email,
        onValueChange = {
            email = it
            hasError = false
        },
        label = { Text("Email address") },
        placeholder = { Text("you@example.com") },
        isError = hasError,
        supportingText = {
            if (hasError) {
                Text(
                    text = errorMessage,
                    modifier = Modifier.semantics {
                        liveRegion = LiveRegionMode.Polite
                    }
                )
            }
        },
        keyboardOptions = KeyboardOptions(keyboardType = KeyboardType.Email),
        modifier = Modifier.semantics {
            if (hasError) error(errorMessage)
        }
    )
}
