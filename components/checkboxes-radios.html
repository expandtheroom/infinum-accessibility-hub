Checkboxes & Radios

Accessible patterns for checkbox and radio button groups, including correct labeling, grouping, and keyboard behavior.

Design guidelines

UX guidelines

  • Labels must always be visible and adjacent to the control — place them to the right of the checkbox or radio, never above or below in isolation. A label that is spatially distant from its control creates confusion for users with low vision or cognitive disabilities.
  • Annotate required groups in design files — indicate which fieldsets require at least one selection, and specify that the requirement indicator (*) must be accompanied by a visible legend explaining its meaning (e.g. "* Required field").
  • Never use a single radio button in isolation. A radio implies mutual exclusivity within a group; a single radio with no alternatives conveys nothing meaningful. Use a checkbox for a single binary choice, or provide at least two radio options.

Visual design guidelines

  • Custom-styled checkboxes and radios must retain all visual states: unchecked, checked, indeterminate (checkbox only), focus, hover, and disabled. When replacing native controls with custom CSS, each state must be explicitly designed — browser defaults no longer apply.
  • Error states must combine color with a secondary indicator — a red border or red text alone fails WCAG 1.4.1 (Use of Color). Add an error icon, an "Error" text label, or an inline error message to communicate the failure without relying on color alone.
  • Touch targets must be at least 44×44px including the label's click area, not just the control itself. Extend the clickable area to the full label text — this is especially important on mobile where precise tapping of small controls is difficult.
  • The indeterminate state must be visually distinct from both checked and unchecked — typically shown as a dash or minus sign inside the checkbox. Do not rely solely on the browser's native rendering; design a custom indeterminate state that works across your component library.

Dev guidelines for web

  • Use <input type="checkbox"> or <input type="radio"> with an associated <label> via matching for/id attributes. Wrapping the input inside the label is an equally valid approach. Never use custom elements with role="checkbox" when a native input will do.
  • Wrap related groups in <fieldset><legend>. Screen readers announce the legend text before each option — e.g. "Preferred contact method, group. Email, radio button, 1 of 3." Without a fieldset and legend, users lose the question context when navigating between options.
  • Indicate required groups using aria-required="true" on at least one input in the group, or on the <fieldset> element itself. Do not rely on an asterisk alone — pair it with a visible legend explaining the convention.
  • Set the indeterminate state via JavaScript: checkboxElement.indeterminate = true. Screen readers announce this as "mixed". Do not use aria-checked="mixed" on a native <input type="checkbox"> — the JavaScript property is the correct mechanism for native inputs.
  • Radio groups use roving tab index — only the selected radio (or the first if none selected) should be in the tab order (tabindex="0"); all others are tabindex="-1". Arrow Up / Arrow Down move focus and selection within the group. Do not make all radios individually tabbable — it creates an unnecessarily long tab sequence.
  • Checkboxes are individually tabbable — each checkbox in a group receives its own Tab stop. Space toggles the checked state. Unlike radio buttons, checking one checkbox does not affect the others.

Dev guidelines for iOS

  • Use .accessibilityElement(children: .combine) on the row container when pairing a label and a checkbox or radio control — this merges the label text and the control state into a single VoiceOver focus target, so users hear "Email, checkbox, unchecked" rather than navigating two separate elements.
  • Apply .accessibilityAddTraits(.isSelected) to the selected radio option and remove it from all others when selection changes. VoiceOver will announce "selected" on the active option and nothing on the rest, which maps to the native radio button mental model.
  • Set .accessibilityValue("checked") or .accessibilityValue("unchecked") explicitly on custom checkbox controls so VoiceOver announces the current state regardless of visual styling. For a three-state checkbox, also supply .accessibilityValue("mixed") when the indeterminate state is active.
  • Mark disabled options with .accessibilityHint("Not available") and .accessibilityAddTraits(.isStaticText) so VoiceOver communicates that the option cannot be interacted with rather than silently omitting it from focus.
  • Announce group validation errors using UIAccessibility.post(notification: .announcement, argument: "...") — for example, "Please select at least one contact method" — immediately after the user attempts to continue without making a required selection.

Example code

import SwiftUI

struct ContactMethodRow: View {
    let label: String
    @Binding var isChecked: Bool

    var body: some View {
        HStack(spacing: 12) {
            Image(systemName: isChecked ? "checkmark.square.fill" : "square")
                .foregroundColor(isChecked ? .accentColor : .secondary)
                .font(.title2)
            Text(label)
                .font(.body)
        }
        .contentShape(Rectangle())
        .onTapGesture { isChecked.toggle() }
        .accessibilityElement(children: .combine)
        .accessibilityLabel(label)
        .accessibilityValue(isChecked ? "checked" : "unchecked")
        .accessibilityAddTraits(.isButton)
        .accessibilityHint("Double-tap to toggle")
    }
}

struct ContactMethodGroup: View {
    @State private var emailSelected = false
    @State private var smsSelected = false
    @State private var phoneSelected = false

    var body: some View {
        VStack(alignment: .leading, spacing: 8) {
            Text("Preferred contact methods")
                .font(.headline)
                .accessibilityAddTraits(.isHeader)
            ContactMethodRow(label: "Email", isChecked: $emailSelected)
            ContactMethodRow(label: "SMS", isChecked: $smsSelected)
            ContactMethodRow(label: "Phone", isChecked: $phoneSelected)
        }
        .padding()
    }
}

Dev guidelines for Android

  • Set Role.Checkbox or Role.RadioButton in a Modifier.semantics block on custom controls so TalkBack announces the correct role. Without an explicit role, a custom composable is treated as a generic region and users lose the interaction affordance cue.
  • Use mergeDescendants = true on the row container when a label Text and a Checkbox or RadioButton composable are siblings — this merges them into a single focus target and TalkBack reads the combined label and state automatically.
  • Set stateDescription for custom or three-state checkboxes — for example, stateDescription = if (checked) "Checked" else "Unchecked" — to ensure TalkBack announces state changes consistently regardless of visual styling or toggle animation.
  • Mark the group label as a heading using Modifier.semantics { heading() } on the Text that acts as the fieldset legend. This allows TalkBack users navigating by headings to jump directly to each group.

Example code

import androidx.compose.foundation.layout.*
import androidx.compose.material3.*
import androidx.compose.runtime.*
import androidx.compose.ui.Alignment
import androidx.compose.ui.Modifier
import androidx.compose.ui.semantics.*
import androidx.compose.ui.unit.dp

@Composable
fun ContactMethodRow(label: String, checked: Boolean, onCheckedChange: (Boolean) -> Unit) {
    Row(
        verticalAlignment = Alignment.CenterVertically,
        modifier = Modifier
            .fillMaxWidth()
            .semantics(mergeDescendants = true) {
                role = Role.Checkbox
                stateDescription = if (checked) "Checked" else "Unchecked"
            }
    ) {
        Checkbox(checked = checked, onCheckedChange = onCheckedChange)
        Spacer(modifier = Modifier.width(8.dp))
        Text(text = label, style = MaterialTheme.typography.bodyLarge)
    }
}

@Composable
fun ContactMethodGroup() {
    val options = remember { mutableStateMapOf("Email" to false, "SMS" to false, "Phone" to false) }
    Column(modifier = Modifier.padding(16.dp), verticalArrangement = Arrangement.spacedBy(4.dp)) {
        Text(
            text = "Preferred contact methods",
            style = MaterialTheme.typography.titleMedium,
            modifier = Modifier.semantics { heading() }
        )
        options.keys.forEach { label ->
            ContactMethodRow(
                label = label,
                checked = options[label] == true,
                onCheckedChange = { options[label] = it }
            )
        }
    }
}
